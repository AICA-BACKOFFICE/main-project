1목표와 원칙

목표

"어떤 기능을 고치려면 폴더 하나만 열면 된다"가 되도록 파일을 다시 묶습니다. 지금은 게시물 기능 하나가 post/, templates/post/, mapper/PostMapper.xml, static/js/block-editor.js, static/css/editor.css에 흩어져 있고, 에디터 JS 한 파일이 1,226줄입니다.

원칙 (우선순위 순)

  1. 동작은 그대로 — 이 작업은 이동·이름 변경·분할만 합니다. 기능 개선은 별도 작업으로 뺍니다.
  2. 기능 우선, 계층은 그 안에서 — 최상위 폴더는 기능(post, editor, media, account …), 그 안에서 Controller/Service/Mapper/모델을 파일명으로 구분합니다.
  3. Java·템플릿·SQL·JS·CSS가 같은 기능 이름을 공유 — post/ 패키지 ↔ templates/post/ ↔ mapper/post/ ↔ static/js/post/ ↔ static/css/post.css처럼 이름만 보고 짝을 찾을 수 있게 합니다.
  4. 큰 파일은 관심사별로 쪼갠다 — 한 파일 300줄 안팎을 기준으로, 넘으면 역할별로 분리합니다.
  5. 잔재는 지운다 — 1줄짜리 자리표시자, Stage0 검증물, 사용하지 않는 CSS 구역을 제거합니다.
  6. 단계마다 mvnw clean verify 통과 — 각 단계가 독립 커밋이 되도록 하고, 실패 시 그 단계만 되돌립니다.
하지 않는 것 모듈 분리(멀티 모듈 Maven), 프레임워크 교체, DB 스키마 변경, 프런트 빌드 도구 도입(번들러)은 이번 범위가 아닙니다. JS는 여전히 <script> 태그로 순서대로 로드합니다.

3Java 패키지 재배치

3.1 account — 인증·계정 통합

auth/(3) + adminuser/(7) + bootstrap/InitialAdminRunner를 account/ 하나로 합칩니다. 로그인 → 사용자 조회 → 임시 비밀번호 변경 → 계정 관리까지 한 흐름이 한 폴더에서 읽힙니다. 클래스 이름은 유지하고 패키지 선언과 import만 바뀝니다.

현재변경 후비고
auth/LoginController, CurrentAdmin, AdminUserDetailsServiceaccount/…SecurityConfig의 import 수정
adminuser/AdminUser, AdminRole, AdminUserForm, AdminUserMapper, AdminUserService, AdminUserController, PasswordControlleraccount/…MyBatis namespace 변경 필요 (4장)
bootstrap/InitialAdminRunneraccount/InitialAdminRunnerbootstrap 패키지 삭제

3.2 post — 책임 분리

PostController(16개 매핑)와 PostService를 세 묶음으로 나눕니다. URL은 전부 그대로이므로 화면·테스트·SecurityConfig의 경로 규칙은 바뀌지 않습니다.

새 클래스가져오는 메서드URL
PostController (유지, 축소)list, createForm, create, editForm, update, changeStatus, addFormOptions/admin/posts, /new, /{id}/edit, /{id}, /{id}/status
PostTrashController ★trash, delete, restore, purge/admin/posts/trash, /{id}/delete, /{id}/restore, /{id}/purge
PostPreviewController ★preview, previewDraft/admin/posts/{id}/preview, POST /admin/posts/preview
version/PostVersionController ★versions, version, restoreVersion (+ VERSION_TIME 포맷터)/admin/posts/{id}/versions/**
PostService (유지, 축소)search, get, getPublished, create, update, apply, blocksOf, blocksOfJson, changeStatus—
PostTrashService ★delete(soft), searchTrash, getDeleted, restore, purgepurge 는 PostVersionService.deleteByPost 호출
version/PostVersionService ★record(post, reason, adminId), versionsOf, version, restorePostService.create/update 가 record 호출
주의 @RequestMapping("/admin/posts") 아래에 /trash(고정 경로)와 /{id}/…(변수 경로)가 서로 다른 컨트롤러로 나뉘어도 Spring MVC는 고정 경로를 우선 매칭하므로 충돌하지 않습니다. 각 컨트롤러에 @ModelAttribute("menu") → "posts"를 넣어 좌측 메뉴 활성 표시를 유지합니다(휴지통은 "trash").

3.3 editor — 블록 모델 독립

BlockContent는 게시물뿐 아니라 템플릿·미리보기·공개 API가 함께 쓰는 "본문 형식" 정의입니다. post/에서 꺼내 editor/로 옮기고, 역할이 드러나게 BlockSanitizer로 이름을 바꾸는 것을 권장합니다(선택). 블록 타입·허용 글꼴 상수는 BlockTypes로 분리해 프런트 JS의 FONTS와 1:1로 대응하는 주석을 둡니다.

3.4 template — Service 계층 추가

다른 기능과 같은 모양이 되도록 PostTemplateService를 만들어 검증·정화·개수 제한·트랜잭션을 옮기고, 컨트롤러는 요청/응답 변환만 남깁니다. 동작·URL·JSON 형식은 동일합니다.

3.5 개명: image → media, api → publicapi

image는 앞으로 첨부파일(PDF 등)까지 담을 수 있도록 media로, api는 내부 JSON 엔드포인트(템플릿·이미지·버전)와 구분되도록 publicapi로 바꿉니다. URL(/admin/images, /api/public)은 그대로 둡니다. 클래스 이름 변경(ImageController → MediaController)은 2차 작업으로 미룹니다.

3.6 삭제

  • stage0/ 전체, bootstrap/SampleDataRunner, test/verification/Stage0WebTest, test/resources/stage0/
  • Stage0DatabaseTest: Stage0 리소스에 의존하므로 함께 삭제(기능 테스트는 BackofficeWebTest가 대신함). 기록이 필요하면 docs/STAGE0_VERIFICATION.md에 이미 남아 있음.
  • src/compatibility: pom 프로파일 egov43-probe와 함께 유지할지 결정. 유지한다면 docs/에 용도를 한 줄 적고, 아니면 삭제.

8단계별 실행 계획과 검증

각 단계는 독립 커밋으로 남기고, 끝날 때마다 .\mvnw.cmd -B -ntp clean verify와 아래 "확인" 항목을 수행합니다. 한 단계가 실패하면 그 단계만 되돌립니다.

단계작업세부확인예상
0정리자리표시자 7개·stage0 테스트·리소스 삭제, src/compatibility 유지 여부 결정, 사용 안 하는 CSS 규칙 grep 후 제거빌드·테스트 통과, 화면 깨짐 없음0.5일
1Java 패키지 이동account 통합, image→media, api→publicapi, BlockContent→editor, PostVersion→post/version. IDE의 "Move/Rename" 리팩터링 사용(import 자동 수정)XML namespace 7개 점검, 로그인→글 저장→이미지 업로드 수동 확인0.5일
2Controller/Service 분할PostTrash·PostPreview·PostVersion 컨트롤러/서비스 분리, PostTemplateService 추출. 메서드 본문은 복사-붙여넣기, 시그니처 유지BackofficeWebTest 전부 통과(URL 불변이므로 수정 없이 통과해야 함), SecurityConfig 변경 없음 확인0.5일

권장 순서의 이유

Java(1·2단계)를 먼저 끝내면 IDE 리팩터링으로 import가 자동 정리되어 가장 안전하고, 리소스(3단계)는 Java의 return 문자열·namespace가 확정된 뒤 옮겨야 두 번 손대지 않습니다. JS 분할(4단계)은 가장 손이 많이 가고 회귀 위험이 커서 다른 단계가 안정된 뒤 마지막에 합니다.

Git 작업 방식

  • 브랜치 refactor/feature-layout에서 단계별 커밋: refactor(0): remove placeholders, refactor(1): move packages …
  • 이동은 반드시 git mv(또는 IDE 이동)로 하여 히스토리가 이어지게 합니다.
  • 각 단계 커밋 메시지에 "동작 변경 없음 / 검증: verify 통과, 화면 N개 확인"을 적습니다.
