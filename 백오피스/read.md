## 1. 목표와 현재 상태

현재 개발 범위는 IA와 시안이 없어도 만들 수 있는 공통 기반과 기본 게시물 관리까지로 잡는다. 로그인·비밀번호 변경·계정 발급·RBAC를 먼저 연결하고, 실제 글을 등록·조회·수정·삭제할 수 있는 기본 게시판을 함께 완성한다. 게시물 기능은 최초 요청에 포함된 필수 기능이며, 이번 작업안에서는 IA 수령을 착수 조건으로 두지 않는다.

현재 요구사항과 IA 후보를 고려해 `SUPER_ADMIN / ADMIN / SUPPORTER` 3단계 역할 구조를 초기 제안안으로 둔다. 역할 수와 세부 권한, 게시물 필드와 삭제 방식은 고객 확정사항이 아니다. 구현에 필요한 최소 가정을 문서화해 개발하고, IA와 운영 정책을 받으면 실제 업무에 맞게 조정한다.

1차 완료 기준은 다음 흐름과 권한 검사, 계정 변경에 따른 세션 처리가 실제로 동작하는 것이다. 공통 기반만 완료한 상태는 중간 단계이며, 현재 개발 범위의 완료에는 기본 게시물 CRUD와 관련 검증이 포함된다.

> 최초 SUPER_ADMIN 생성 → 로그인 및 임시 비밀번호 변경 → ADMIN 또는 SUPPORTER를 선택해 계정 발급 → 발급받은 계정의 로그인 및 비밀번호 변경 → 허용 범위에서 글 등록·목록/상세 조회·수정·삭제

최초 전달받은 ZIP의 프로젝트 파일은 `README.md` 한 개였다. 현재는 0단계용 Maven Wrapper·빌드 설정, 최소 서버와 기동 확인 화면, 기술 검증 테스트를 추가했다. 업무 기능·업무 DB 스키마·배포 설정은 아직 없으며, 기존 서비스 소스와 화면 시안도 전달받지 못했다. 테스트용 H2 테이블은 기술 검증에만 사용하며 운영 DB 선택을 확정한 것이 아니다.

이 문서는 구현 전 협의용 초안이다. 현재 작업 범위와 초기 구현 가정을 정리한 것이며, 실제 계약·납품 범위나 최종 IA가 승인되었다는 뜻은 아니다. 기존 README는 원본으로 보존한다.

연결된 비교 문서는 최초 제안 작성 시점의 비교를 보존한 자료다. 현재 개발 범위는 이 문서의 5장과 10장을, 역할별 초기 권한은 6장을 기준으로 한다.

## 2. 요구사항과 제안의 구분

### 전달받은 전체 기능 요구사항

- 로그인과 본인 비밀번호 변경
- 일반 회원가입 없이 시스템 관리자가 계정을 발급하는 방식
- 최상위 관리자의 서브 계정 생성
- 최상위 관리자와 서브 관리자의 권한 차등(RBAC)
- 게시물 등록·수정·삭제: 현재 개발 범위에 포함하고, 사용을 위한 목록·상세 조회도 함께 구현

위 기능을 현재 작업의 기준으로 삼아 공통 기반과 기본 게시판을 구현한다. 기본 게시물 테이블·요청 처리·화면·권한 검증까지 포함한다. IA 이후에는 기본 게시판을 실제 메뉴별 콘텐츠 종류·필드·운영 흐름에 맞게 조정하고, 필요한 추가 기능의 범위를 정한다.

정확한 역할 수, SUPPORTER의 분리 여부, ADMIN과 SUPPORTER의 게시물 접근 범위까지 확정된 것은 아니다. 3개 역할과 게시물 권한은 초기안으로 구현·검증하되, 고객의 최종 정책으로 간주하지 않는다. 권한 변경에 대응할 수 있게 판단 위치를 모으고, IA·운영 정책 확인 시 갱신한다.

### 전달받은 기술 조건

| 항목 | 요청 버전 |
| --- | --- |
| 공통 기반 | 전자정부 표준프레임워크 RTE 4.3.0, 관리자·사용자 모듈 공통 |
| Java | 17 |
| Spring Boot | 3.4.5 |
| Spring Framework | 6.2.6 |
| Spring Security | 6.4.5 |
| 내장 Tomcat | 10.1.40 |

요청 버전은 임의로 변경하지 않는다. 0단계에서 위 Spring 구성과 Java 17의 빌드·기동, RTE 4.3.0의 일부 서비스·데이터 접근 기능을 검증했다. RTE 전체나 기존 사용자 모듈까지 포함한 동시 적용 가능성을 확인한 것은 아니다. 검증에 사용한 의존성 조정과 적용 범위는 별도 결과 문서에 기록한다.

### 이 문서에서 제안하는 선택

Thymeleaf 화면, 세션 인증, MyBatis, Maven Wrapper, Flyway를 초기안으로 삼는다. 운영 DB, 배포 환경, 기존 서비스의 인증 연동은 확인 후 확정한다. 기술 검증 결과에 따라 라이브러리의 구체 버전을 정한다.

권한은 `SUPER_ADMIN / ADMIN / SUPPORTER` enum 또는 이에 준하는 단순한 역할값으로 시작하는 것을 제안한다. 역할과 실제 허용 행위·대상 범위를 구분하고, 인증·계정·게시물의 권한 판단을 한정된 위치에 모은다. ADMIN의 타인 게시물 수정·삭제 허용 등 세부 권한은 6장의 초기안으로 개발하되 최종 업무 정책 확인 대상으로 둔다. 역할이 2개로 줄거나 명칭·책임이 바뀔 수 있으므로, 이를 고객의 최종 권한 체계로 간주하지 않는다.

## 3. 첫 단계: 기술 구성 검증

전자정부 공식 4.3 마이그레이션 가이드는 Spring Framework 5.3.37을 기준으로 설명한다. 따라서 RTE 4.3.0을 Spring Boot 3.x / Jakarta EE 10 기반이라고 설명할 근거는 없다. [전자정부 공식 가이드](https://www.egovframe.go.kr/wiki/doku.php?id=egovframework:rtemigration4.3)

Spring Boot 3.4.5의 공식 릴리스에는 Spring Framework 6.2.6, Spring Security 6.4.5, Tomcat 10.1.40이 명시되어 있다. 이 Spring 구성에 RTE 4.3.0을 함께 적용하는 부분이 검증 대상이다. [Spring Boot 3.4.5 릴리스](https://github.com/spring-projects/spring-boot/releases/tag/v3.4.5)

검증 순서는 다음과 같다.

1. 담당자에게 RTE 4.3.0과 Boot 3.4.5가 모두 필수인지, 기존에 검증된 `pom.xml` 또는 표준 프로젝트가 있는지 확인한다.
2. 실제 사용할 RTE 모듈을 선정한다. 이름만 의존성에 추가하지 않고 서비스·데이터 접근 등 사용 지점을 정한다.
3. 최소 Maven 프로젝트를 만들고 의존성 트리에서 Spring 중복 버전과 Servlet/Jakarta 관련 충돌을 확인한다.
4. Java 17에서 빌드와 서버 기동, 선택한 RTE 기능, MyBatis DB 조회, 트랜잭션 롤백, 인증이 필요한 경로의 접근 차단을 확인한다.
5. 통과한 조합과 사용 범위를 기록한 뒤 공통 프로젝트에 반영한다. 충돌이 있으면 재현 결과와 필요한 조정안을 정리해 기술 조건을 확정한다.

일부 RTE 라이브러리의 기동 성공이 RTE 전체 또는 기존 사용자 모듈과의 호환성을 보장하지는 않는다. 이 검증을 진행하는 동안 기능 범위, 권한표, 기본 화면 구성과 협업 규칙은 정리할 수 있다.

### 0단계 수행 결과 (2026-09-21)

- 기본 프로젝트: Java 17에서 빌드·내장 Tomcat 기동·Thymeleaf 렌더링, 요청한 Spring 관련 버전, 미허용 경로 차단을 확인했다.
- 데이터 접근: 테스트 전용 H2에서 MyBatis 조회, Flyway 마이그레이션, Spring 트랜잭션의 커밋·롤백을 확인했다. PostgreSQL 16과 운영 DB는 아직 검증하지 않았다.
- RTE: 별도 `egov43-probe` Maven 프로필에서 `psl.dataaccess`와 `fdl.cmmn` 4.3.0을 사용해 매퍼 조회·롤백과 서비스의 메시지 예외 처리, 기존 `javax.annotation.Resource` 주입을 확인했다. 기본 테스트 4건과 RTE 추가 테스트 3건이 통과했다.
- 의존성 조정: Boot의 버전 관리, MyBatis-Spring 3.0.4 선택과 일부 전이 의존성 제외를 적용한 실험이다. RTE 원본 POM 전체를 그대로 적용한 결과나 공식 지원 조합으로 해석하지 않는다.
- 범위: 실행 JAR는 최소 Boot 기동 확인용이다. RTE와 DB 관련 라이브러리는 기술 검증용 테스트 범위에 두었으며, 업무용 RTE·DB 설정은 아직 반영하지 않았다. 로그인 화면·계정 발급·권한 역할값·게시물 CRUD는 없다.

실행 명령과 검증 범위는 [0단계 검증 결과](docs/STAGE0_VERIFICATION.md)를 따른다. 다음 단계 전에 RTE/Boot 버전의 필수 여부, 검증된 표준 프로젝트 유무, RTE 적용 범위와 DB를 담당자에게 확인해야 한다. 일부 검증 통과를 근거로 기술 조건 전체가 확정되었다고 표시하지 않는다.

## 4. 공통 기반과 기본 게시판의 초기 구현 구조

| 항목 | 제안 | 적용 조건·이유 |
| --- | --- | --- |
| 애플리케이션 | 백오피스 단일 애플리케이션 | 초기 개발과 배포 단위를 단순하게 유지 |
| 화면 | Thymeleaf 서버 렌더링 | 시안 없이도 목록·폼 중심의 관리 기능 구현 가능 |
| 인증 | Spring Security 세션 인증 | 동일 서비스의 관리자 웹에서 로그인 상태를 서버가 관리 |
| 데이터 접근 | MyBatis | SQL을 명시적으로 관리하고 기존안과 일관성 유지 |
| DB | 운영 DB 확인 후 확정 | 미정이면 개발용 PostgreSQL 16을 임시 사용 |
| 스키마 관리 | Flyway | DB 확정 후 해당 DB에서 동작하는 마이그레이션 작성 |
| 빌드 | Maven Wrapper | 두 개발자가 같은 빌드 도구 사용 |
| CI | PR에서 빌드·테스트 | 배포 자동화는 운영 환경 확정 후 추가 |

Spring Security는 세션을 통한 인증 상태 유지를 지원한다. 세션 방식의 선택은 단일 관리자 웹이라는 현재 조건을 바탕으로 한 설계 제안이며, SSO 등 기존 인증 체계가 확인되면 재검토한다. [Spring Security 세션 관리 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)

관리자·사용자 모듈이 같은 기술 기반을 사용한다는 조건은 유지한다. 현재 개발 대상은 백오피스이며, 공개 사용자 화면과 API의 신규 구현은 기존 서비스의 연결 방식 확인 후 범위를 정한다. 패키지 분리만으로 서비스 연동이 완료되었다고 판단하지 않는다.

IA 이전에 구현할 공통 기반과 기본 게시판의 예상 구조는 다음과 같다. 패키지명은 기존 서비스의 규칙을 확인한 뒤 확정한다.

```text
backoffice/
├── pom.xml
├── mvnw / mvnw.cmd
└── src/
    ├── main/
    │   ├── java/<확정할 기본 패키지>/
    │   │   ├── common/         # 공통 오류 처리·설정·보안·감사 기록
    │   │   ├── auth/           # 로그인·로그아웃·비밀번호
    │   │   ├── adminaccount/   # 관리자·서포터즈 계정·권한
    │   │   └── post/           # 기본 게시물 등록·조회·수정·삭제
    │   └── resources/
    │       ├── templates/     # 공통 레이아웃과 기능별 화면
    │       ├── static/
    │       ├── mapper/
    │       └── db/migration/
    └── test/
```

각 기능은 화면/요청 처리, 업무 규칙, 데이터 접근을 구분한다. RTE 기반 클래스 상속과 매퍼 구성은 기술 검증에서 확인한 방식으로 적용한다.

기본 게시판의 매퍼·서비스·컨트롤러·템플릿은 현재 구현한다. 인증·계정·게시물에 필요한 공통 코드를 마련하고, IA 이후 콘텐츠별 필드·화면·업무 규칙을 추가하거나 조정한다. 범용 콘텐츠 엔진이나 모든 메뉴를 동적으로 생성하는 시스템까지 선행 구현하지 않는다.

## 5. 현재 개발 범위와 IA 이후 범위

### 지금 개발할 공통 기반과 기본 게시판

| 기능 | 1차 구현 내용 | 기본 화면·산출물 |
| --- | --- | --- |
| 프로젝트·데이터 접근 | 빌드·환경 설정, DB 연결, MyBatis·트랜잭션·마이그레이션 실행 기반 | 두 개발자가 재현할 수 있는 실행 환경 |
| 인증 | 로그인·로그아웃·본인 비밀번호 변경, 세션 관리 | 로그인, 비밀번호 변경 |
| 최초 계정 | 초기 최상위 관리자 1회 생성 | 별도 공개 가입 화면 없음 |
| 계정 관리 | SUPER_ADMIN의 계정 목록·ADMIN/SUPPORTER 선택 생성·이름 변경·비활성화·비밀번호 초기화·별도 역할 변경 | 계정 목록, 등록/수정, 별도 역할 변경 절차 |
| 권한 | 단순 역할값, 계정 관리 접근 제한, 게시물 전체/본인 범위 검사, 역할·상태 변경 시 세션 처리 | 공통 권한 검사와 역할별 시나리오 검증 |
| 기본 게시판 | DB 저장을 포함한 글 등록·목록/상세 조회·수정·삭제, 목록 페이징 | 실제 사용할 수 있는 기본 게시판 화면·테이블·요청 처리 |
| 공통 화면 | 기본 레이아웃·메뉴 영역·표·입력 폼 | 공통 진입 화면, 인증·계정·게시물 화면에 사용할 구성 |
| 공통 처리 | 입력 검증, 오류·접근 거부 처리, 필요한 로그 | 공통 오류 형식과 기본 오류 화면 |
| 감사 기록 | 계정 생성·역할/활성 상태 변경·비밀번호 초기화·게시물 삭제 기록 | 기록 저장과 검증, 전용 조회 화면은 후속 범위 |
| 개발 검증 | 인증·계정·게시물 테스트와 CI·실행 문서 | PR 빌드·테스트, 환경 설정과 기본 사용 안내 |

계정 생성 화면은 SUPER_ADMIN에게만 제공하고 ADMIN 또는 SUPPORTER를 선택하는 초기안이다. SUPER_ADMIN 승격은 일반 생성 화면에서 선택하지 않고 별도 역할 변경 절차로 처리한다. 로그인 후에는 본인 정보·비밀번호 변경·로그아웃과 허용된 게시물 기능을 이용하고, 계정 관리 메뉴는 SUPER_ADMIN에게만 제공한다.

### IA 없이 진행할 기본 게시판의 개발 가정

| 항목 | 현재 구현할 초기안 | 이후 확인할 내용 |
| --- | --- | --- |
| 게시판 수 | 단일 기본 게시판 | 실제 메뉴·콘텐츠 종류와 분리 필요 여부 |
| 필드 | 제목, 일반 텍스트 본문, 작성자, 생성/수정 시각 | 콘텐츠별 추가 필드·분류·표시 방식 |
| 조회 | 목록·페이징·상세 | 검색·필터·정렬 등의 요구 |
| 등록·수정 | 입력 검증 후 DB 저장, 작성자는 로그인 계정 기준 | 최종 입력 규칙·편집 방식 |
| 삭제 | 삭제 시각을 기록하고 일반 목록·상세·수정에서 제외하는 방식 제안 | 실제 삭제·보존·복구 정책 |
| 접근 범위 | 로그인한 계정에 6장의 초기 권한 적용 | ADMIN의 타인 글 편집 여부 등 최종 정책 |
| 화면 | 기본 표와 입력 폼 | 최종 메뉴 구성과 시안 |

이 가정으로 실제 등록·조회·수정·삭제 흐름을 구현하고 테스트한다. 화면만 있는 시제품이나 메모리 데이터 예제로 완료 처리하지 않는다. 본문은 일반 텍스트로 저장·표시하고 HTML로 실행되지 않도록 처리한다. 삭제 복구 화면은 현재 범위에 포함하지 않는다. 필드와 삭제 정책은 고객 확정사항이 아니므로 IA·운영 정책 확인 시 필요한 코드와 마이그레이션을 조정한다.

### IA·시안 이후 조정하거나 추가할 범위

IA가 나오면 기본 게시판을 실제 콘텐츠 종류·필드·관계·메뉴별 업무 흐름에 맞게 조정한다. 현재 코드를 모든 콘텐츠에 그대로 적용할 수 있다고 가정하지 않는다. 역할별 권한과 공개·승인·삭제 정책을 재검토하고, 달라진 정책에 맞춰 데이터 구조와 검증을 갱신한다.

검색·이미지·첨부·HTML 에디터·게시 승인 등은 필요 확인 후 범위를 정한다. 일반 회원가입, 소셜 로그인, 이메일 인증, 댓글·통계, 공개 사용자 API도 현재 구현 범위에 포함하지 않는다. 시안이 나오면 기본 화면의 디자인·배치를 적용한다. 기본 게시물 CRUD의 착수와 완료를 IA나 최종 시안 수령까지 미루지 않는다.

## 6. 권한 정책

### 역할별 초기 권한안

아래 표는 현재 구현·검증할 초기안이다. 3개 역할과 세부 권한은 현재 요구사항과 IA 후보를 고려한 제안이며 고객 확정사항은 아니다. 역할은 계정의 분류이고, 허용 행위와 대상 범위는 별도의 판단 기준으로 관리한다. ADMIN과 SUPPORTER의 게시물 권한은 개발 가정을 적용하되 최종 업무 정책 확인 대상으로 유지한다.

| 허용 행위·대상 범위 | SUPER_ADMIN | ADMIN | SUPPORTER |
| --- | --- | --- | --- |
| 로그인·로그아웃·본인 비밀번호 변경 | 가능 | 가능 | 가능 |
| 공통 진입 화면·본인 정보 확인 | 가능 | 가능 | 가능 |
| 관리자·서포터즈 계정 목록 조회 | 가능 | 불가 | 불가 |
| ADMIN/SUPPORTER 계정 생성 | 역할을 선택해 생성 가능 | 불가 | 불가 |
| 다른 계정의 이름 변경·비활성화·비밀번호 초기화 | 가능 | 불가 | 불가 |
| 역할 변경·SUPER_ADMIN 승격 | 별도 역할 변경 절차에서 가능 | 불가 | 불가 |
| 전체 게시물 목록·상세 조회 | 가능 | 가능 | 불가 |
| 본인 게시물 목록·상세 조회 | 가능 | 가능 | 가능 |
| 게시물 등록 | 가능 | 가능 | 가능 |
| 본인 게시물 수정·삭제 | 가능 | 가능 | 가능 |
| 타인 게시물 수정·삭제 | 가능 | 허용을 기본 제안으로 구현, 최종 정책 확인 필요 | 불가 |

SUPER_ADMIN은 전체 게시물을 관리하고, ADMIN은 전체 조회·등록·수정·삭제를 허용하는 초기안을 적용한다. SUPPORTER는 등록과 본인 게시물 조회·수정·삭제만 허용하며, 타인 게시물 접근과 계정 관리는 차단한다. 정책이 바뀌면 권한 판단·조회 범위·테스트를 함께 변경한다.

향후 관리자 운영 기능은 SUPER_ADMIN을 기본 접근 역할로 제안하되 메뉴·행위별 범위는 IA 이후 확인한다. 감사 기록 전용 조회 화면도 SUPER_ADMIN 대상의 후속 범위로 두며, 이 두 항목은 기본 게시물 CRUD의 현재 완료 조건에 포함하지 않는다.

### 단순한 역할 구조와 권한 판단 위치

1차 구현은 계정별로 `SUPER_ADMIN / ADMIN / SUPPORTER` 중 하나를 저장하는 enum 또는 이에 준하는 단순한 구조를 제안한다. 이를 위해 `roles`, `permissions` 테이블이나 별도의 권한 편집 시스템을 만들지 않는다.

권한 판단은 Spring Security 설정의 경로별 접근 검사와 서비스 계층의 공통 권한 검사 등 한정된 위치에서 관리한다. 계정 관리와 게시물 조회·등록·수정·삭제 등의 행위, 전체/본인이라는 대상 범위를 기준으로 검사한다. 역할을 직접 비교하는 조건을 각 컨트롤러·화면·업무 코드에 반복하지 않는다. 화면의 메뉴·버튼 노출도 같은 정책을 따르되 최종 검사는 서버에서 수행한다. 역할의 이름이나 순서만으로 권한을 자동 상속한다고 가정하지 않는다.

SUPPORTER의 본인 게시물 범위는 목록 조건·개수·페이징과 상세·수정·삭제 시 작성자 검사에 모두 적용한다. 작성자 식별자는 로그인 계정을 기준으로 판단하고, 게시물·작성자 요청값을 바꾸어 권한을 넓힐 수 없게 한다. 이 검사는 기본 게시판의 현재 구현 범위에 포함한다.

향후 역할을 2개로 줄이거나 역할명이 변경되면, 역할값과 허용 행위의 연결을 정리하고 기존 계정의 역할값 전환, 영향받는 세션, 권한 검증을 함께 점검한다. 역할 변경에 대응하기 위해 지금부터 범용 권한 시스템을 구현하지 않는다.

### 계정 생성·역할 변경과 보호 장치

SUPER_ADMIN이 신규 계정의 역할을 ADMIN 또는 SUPPORTER 중 선택해 생성하는 초기안이다. 일반 계정 생성에서는 SUPER_ADMIN을 선택하거나 요청값으로 지정할 수 없도록 화면과 서버 모두에서 제한한다. 최초 SUPER_ADMIN의 시스템 초기화는 별도이며, 이후 SUPER_ADMIN 승격은 권한을 확인하는 별도의 역할 변경 절차를 통해서만 수행한다. 해당 절차의 화면과 운영 방식은 담당자 확인 후 구체화한다.

마지막 활성 SUPER_ADMIN은 비활성화하거나 강등할 수 없으며, 자기 자신의 역할·활성 상태도 변경할 수 없게 한다. 역할 변경 가능 행위에도 이 제한을 우선 적용한다. 마지막 관리자 보호는 동시 요청에서도 유지되도록 트랜잭션과 잠금 전략을 적용한다.

## 7. 계정과 로그인 처리

### 최초 관리자와 임시 비밀번호

- 빈 시스템에 한해 명시적인 초기화 설정으로 최초 SUPER_ADMIN을 생성한다. 재기동 시 중복 생성하지 않는다.
- 초기 비밀번호는 설정/비밀값으로 주입하고 코드·문서·로그에 실제 값을 남기지 않는다. 초기화 후 해당 설정을 제거한다.
- 일반 계정 생성은 SUPER_ADMIN이 ADMIN 또는 SUPPORTER를 선택하는 초기안을 따른다. 서버에서 생성 권한과 선택 가능한 역할값을 확인하며, 일반 생성 요청을 변조해 SUPER_ADMIN을 만들 수 없도록 한다.
- 신규 계정과 비밀번호 초기화에는 예측하기 어려운 임시 비밀번호를 발급하고, 발급 담당자에게 한 번만 표시한다. DB에는 BCrypt 해시만 저장한다. 계정 비활성화와 타인 계정의 비밀번호 초기화는 SUPER_ADMIN에게만 허용하며 6장의 보호 장치를 적용한다.
- 세 역할 모두 임시 비밀번호 계정은 변경 전까지 비밀번호 변경과 로그아웃 등 필요한 경로만 사용할 수 있게 한다. 서버에서 화면 요청과 업무 요청 모두를 제한한다.
- 본인 비밀번호 변경에는 현재 비밀번호 확인을 요구한다. 변경 성공 후 기존 세션을 무효화하고 새 비밀번호로 다시 로그인하게 한다.

### 기존 로그인 상태에 변경 사항 반영

세션 인증으로 바꾸는 것만으로 계정 비활성화나 권한 변경이 기존 로그인에 자동 반영되지는 않는다. 이를 구현 대상으로 명시한다.

초기안은 `users.auth_version`을 두고 로그인 시의 버전을 세션에 저장하는 것이다. 비밀번호 변경/초기화, 역할 변경, 비활성화 시 버전을 증가시킨다. 이후 보호된 요청에서는 인가 전에 계정의 존재·활성 상태와 버전을 DB로 확인하고, 불일치하면 세션을 무효화한다. 삭제되거나 비활성화된 계정은 재로그인도 허용하지 않는다. 이 방식의 초기 비용은 인증된 요청마다 계정 조회가 발생하는 것이다.

ADMIN과 SUPPORTER 사이의 역할 변경 및 SUPER_ADMIN 승격·강등에도 같은 처리를 적용한다. 현재 단계에서 계정 관리와 기본 게시물 접근 모두에 적용한다. 예를 들어 ADMIN을 SUPPORTER로 변경하면 기존 세션이 차단되고, 다시 로그인한 뒤에는 본인 게시물만 관리할 수 있어야 한다. 역할 변경 절차에서도 마지막 활성 SUPER_ADMIN 보호와 자기 역할·활성 상태 변경 제한을 유지한다.

개발 환경은 단일 인스턴스의 서버 세션을 사용한다. 재기동 시 로그아웃되는 동작을 허용한다. 다중 인스턴스가 필요한 운영 환경에서는 공유 세션 저장 방식을 별도로 정한다.

### 요청 보호

상태를 변경하는 요청에는 CSRF 검증을 적용하며 GET으로 생성·수정·삭제·로그아웃을 처리하지 않는다. Thymeleaf 폼과 추가하는 비동기 요청에 CSRF 토큰을 포함한다. Spring Security는 폼 및 JavaScript 요청에 대한 CSRF 처리 방법을 제공한다. [공식 CSRF 문서](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)

운영에서는 HTTPS와 HttpOnly/Secure 세션 쿠키를 사용하고 SameSite 정책을 설정한다. 로그인 성공 시 세션 ID를 갱신하고, 로그아웃 시 세션을 무효화한다. 비밀번호 원문과 세션 식별자는 감사 기록에 남기지 않는다. 로그인 실패 횟수 제한·잠금과 세션 만료 시간은 운영 정책에 맞춰 설정값으로 관리한다.

## 8. 공통 기반과 기본 게시물의 데이터·요청 처리

현재 설계·구현할 업무 테이블은 인증·계정, 기본 게시물, 최소 감사 기록에 필요한 범위로 잡는다. 아래 게시물 필드는 IA 이전의 개발 가정이다.

| 업무 테이블 | 주요 항목 |
| --- | --- |
| users | 식별자, 로그인 식별값, 이름, 비밀번호 해시, role(SUPER_ADMIN / ADMIN / SUPPORTER 초기안), 활성 여부, 비밀번호 변경 필요 여부, auth_version, 실패 횟수/잠금 시각, 생성자, 생성/수정 시각 |
| posts | 식별자, 제목, 일반 텍스트 본문, 작성자, 생성/수정 시각, deleted_at(삭제 시각 기록 초기안) |
| audit_logs | 식별자, 행위자, 행위, 대상 종류/식별자, 필요한 변경 내역, 발생 시각 |

`posts`의 마이그레이션·매퍼·서비스·컨트롤러와 기본 화면을 현재 구현한다. 등록·조회·수정·삭제가 실제 DB에서 동작해야 하며, 로그인한 작성자와 역할별 조회·변경 범위를 적용한다. 삭제 시각을 기록하는 초기안에서는 삭제된 글을 일반 목록·상세·수정 대상에서 제외한다. IA 이후 콘텐츠별 추가 필드·관계·정책이 정해지면 필요한 마이그레이션과 코드 변경을 진행한다.

`users.role`은 계정당 하나의 역할값을 저장하는 초기안이다. 애플리케이션 enum 또는 이에 준하는 제한된 값으로 관리하고, 역할별 허용 행위는 중앙화한 보안 설정·서비스 정책으로 연결한다. `roles`, `permissions` 및 역할-권한 연결 테이블은 1차에 추가하지 않는다. DB 컬럼 타입과 값 검증 방식은 운영 DB 확정 후 정하며, DB 고유 enum 사용까지 확정한 것은 아니다. 역할 수나 명칭이 바뀌면 기존 계정값의 전환 기준과 필요한 마이그레이션을 함께 정한다.

세션 인증을 선택하므로 JWT용 `refresh_tokens` 테이블은 만들지 않는다. 공유 세션 저장소 도입 시에는 해당 방식에 필요한 저장 구조를 추가한다. 식별자 타입, 자동 증가 방식, 인덱스, DB별 SQL은 운영 DB 확정 후 정한다. 로그인 식별값은 기존안의 이메일을 임시안으로 두되, 회사 계정 ID 사용 여부를 확인한다.

입력 검증과 함께 로그인 식별값 중복, 필수값, 게시물 작성자 등 참조 관계를 DB 제약으로도 보호한다. 계정 변경·게시물 삭제와 해당 감사 기록은 각각 같은 트랜잭션에서 처리한다. 감사 기록은 최소한 누가 어떤 대상을 어떻게 변경했는지 확인할 수 있어야 한다.

현재 요청 경로는 `/login`, `/logout`, `/account/password`, `/admin/accounts`, `/admin/posts`로 제안한다. 공통 진입 화면과 실제 하위 경로·메서드는 공통 프로젝트에서 정한다. 기본 게시물 목록·상세·등록·수정·삭제 요청 처리를 포함한다. 화면은 MVC 컨트롤러와 폼 전송을 기본으로 하고, 필요한 비동기 기능에만 JSON 엔드포인트를 추가한다.

`/admin` 경로명 자체를 ADMIN 역할만 접근할 수 있다는 뜻으로 사용하지 않는다. 계정 관리 경로는 SUPER_ADMIN만 접근하고, 공통 진입 화면과 본인 비밀번호 변경은 세 역할이 이용한다. 게시물 경로는 세 역할이 6장의 초기 행위·대상 범위에 맞게 이용하며, 목록과 개별 게시물 요청 모두 서버에서 검사한다.

화면 접근 시 미인증 상태는 로그인 화면으로 안내하고, 권한이 없으면 접근 거부를 표시한다. JSON 엔드포인트를 추가한다면 401/403을 구분하고 `{ "code": "...", "message": "..." }` 오류 형식을 맞춘다. JWT 토큰 재발급 API와 모든 화면에 대응하는 별도 REST API는 초기 필수 항목으로 두지 않는다.

## 9. 두 사람의 작업 분담

공통 프로젝트를 먼저 함께 실행해 본 뒤 인증·계정·권한과 기본 게시판으로 나눈다. 각 담당자는 자신의 기능에서 서버·화면·검증을 함께 책임진다. 공통 레이아웃과 데이터 접근 설정 등 공유 작업은 초기 계약을 맞춘 뒤 분담한다.

| 구분 | 책임 범위 |
| --- | --- |
| 함께 | 버전 검증, DB 연결·MyBatis·마이그레이션 설정, 계정·게시물 스키마, 초기 권한표, 공통 레이아웃·오류·감사 처리 계약, Git·CI 규칙 |
| 담당 A | 인증, 세션, 최초 SUPER_ADMIN, ADMIN/SUPPORTER 선택 생성, 별도 역할 변경, 공통 권한 검사, 인증·계정 화면과 검증 |
| 담당 B | 기본 게시물 테이블·매퍼·서비스·컨트롤러, 목록·상세·등록·수정·삭제 화면, 공통 권한 검사를 이용한 전체/본인 범위 적용과 검증 |
| 함께 | 계정·게시물 삭제 감사 기록 연결, 로그인부터 게시물 관리까지 통합 검증, 공통 화면 정리, CI·실행 문서 |

담당 A는 인증 계정 식별자·역할값·권한 확인 방법을 먼저 정하고, 담당 B는 이 계약에 맞춰 게시물 기능을 구현한다. 공통 기반을 완전히 고도화할 때까지 게시물 작업을 기다리게 하지 않는다. 게시물 구현에 필요한 인증·데이터 접근 계약을 맞추면 두 작업을 병행한다.

공유 파일의 수정 담당과 DB 마이그레이션 번호를 변경 전에 조율한다. 공통 레이아웃은 두 기능에서 함께 사용하며, 별도의 범용 화면·콘텐츠 엔진을 만들지 않는다. IA 이후 실제 메뉴별 콘텐츠 요구가 정해지면 추가 작업을 다시 분담한다.

협업은 원격 저장소를 clone해 시작한다. 기능 브랜치와 PR을 사용하고, 공통 코드의 동시 수정 범위를 작게 유지한다. 실제 비밀번호·DB 접속 비밀값은 저장소에 넣지 않으며 예시 설정만 공유한다.

## 10. 개발 순서와 완료 기준

### 전체 1차 개발 계획: 공통 기반과 기본 게시물 CRUD 완료

이번 작업은 아래 0단계와 그 검증에 필요한 최소 프로젝트까지만 수행했다. 단계 1의 업무용 DB·공통 화면 구축, 단계 2~4의 기능 구현·통합 검증은 후속 작업이다. 0단계의 제한된 기술 검증은 통과했으며, 담당자의 표준 구성·적용 범위 확인은 남아 있다.

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 0 | 기술 구성 검증·초기 가정 정리 | 실제 사용할 조합과 RTE 범위의 최소 검증 통과, 역할·게시물 개발 가정과 미확정 정책 기록 |
| 1 | 공통 프로젝트·DB·기본 화면 | 두 개발자 환경에서 같은 절차로 빌드·기동 가능, 인증·계정·게시물의 데이터 접근과 공통 화면 기반 마련 |
| 2 | 인증·계정·권한 | SUPER_ADMIN이 ADMIN/SUPPORTER를 발급하고 각 계정으로 로그인 가능, 계정 제한·역할 변경·세션 처리 동작 |
| 3 | 기본 게시판 | 실제 DB와 화면으로 등록·목록/상세 조회·수정·삭제 가능, 초기 권한·작성자 범위와 삭제 처리가 동작 |
| 4 | 통합·검증 | 아래 필수 시나리오 통과, 실제 실행·테스트·사용 절차와 미확정 정책 문서화 |

단계 2와 3은 필요한 공통 계약이 정리되면 병행할 수 있다. 인증·계정만 동작하는 상태는 중간 완료다. 현재 개발 범위의 완료에는 기본 게시물 CRUD와 권한 검증이 반드시 포함된다. IA나 최종 시안이 없다는 이유로 기본 게시판 착수·검증을 후속 단계로 넘기지 않는다. 기술 조합 등 실제 기반의 미해결 사항은 별도로 검증·조정한다.

필수 확인 시나리오는 다음과 같다. 미확정 권한과 게시물 정책은 문서의 초기안으로 검증하고, 최종 정책이 달라지면 구현과 기대 결과를 함께 갱신한다.

- 빈 시스템에 최초 SUPER_ADMIN이 한 번만 생성되고 재기동 시 중복 생성되지 않는다.
- SUPER_ADMIN이 ADMIN과 SUPPORTER를 각각 선택해 생성하고, 발급받은 계정이 임시 비밀번호 변경 후 글을 등록·조회·수정·삭제하는 흐름이 동작한다.
- 세 역할 모두 로그인·로그아웃·본인 비밀번호 변경이 가능하고, 미인증 상태에서는 보호된 화면·요청에 접근할 수 없다.
- ADMIN과 SUPPORTER가 요청을 직접 조작해도 계정 목록·생성·비활성화·타인 비밀번호 초기화·역할 변경 기능에 접근할 수 없다.
- 일반 계정 생성 요청의 SUPER_ADMIN 지정이 차단되고, 승격은 별도 역할 변경 절차에서만 가능하다. 자기 역할·활성 상태 변경도 차단된다.
- SUPER_ADMIN은 전체 게시물을 관리한다. ADMIN은 전체 조회·수정·삭제 허용이라는 초기안대로 동작하며, 최종 정책 확인 항목을 기록한다.
- SUPPORTER의 목록·개수·페이징·상세에는 본인 게시물만 포함된다. 타인의 게시물 식별자를 직접 보내도 조회·수정·삭제할 수 없다.
- 등록·수정 요청의 작성자 식별자를 변조해 소유권과 권한 범위를 바꿀 수 없다.
- 등록·수정 내용은 DB에 저장되어 다시 조회해도 유지된다. 삭제된 글은 목록·상세·수정 대상에서 제외된다.
- 비활성화·역할 변경·비밀번호 초기화 후 기존 세션의 다음 보호된 요청이 차단된다. 비활성 계정은 재로그인도 할 수 없다.
- ADMIN에서 SUPPORTER로 변경 후 재로그인하면 본인 게시물 범위만 허용된다. SUPER_ADMIN 승격·강등 후 계정 관리 권한도 새 역할에 맞게 적용된다.
- 임시 비밀번호 변경 전 허용 경로 외 요청과 CSRF 토큰 없는 변경 요청이 차단된다.
- 마지막 활성 SUPER_ADMIN 보호가 동시 변경 요청에서도 유지된다.
- 계정 변경·게시물 삭제와 해당 감사 기록이 함께 저장되고, 입력 오류·접근 거부가 정한 방식으로 처리된다.
- 현재 DB에서 계정·게시물·감사 기록용 마이그레이션과 조회·변경·롤백이 동작한다. 임시 개발 DB를 사용했다면 운영 DB 검증은 별도로 남긴다.

### 후속 단계: IA에 따른 업무 기능 조정과 시안 반영

IA를 받으면 실제 콘텐츠 메뉴·필드·관계·업무 흐름을 현재 기본 게시판과 비교한다. 그대로 쓸 부분과 변경·추가할 부분을 정하고, 필요한 데이터 마이그레이션·화면·권한·테스트를 갱신한다. 검색·첨부·에디터·게시 승인 등은 확인된 요구에 따라 범위를 정한다.

시안이 나오면 공통 레이아웃과 화면 디자인·배치를 적용한다. 실제 서비스 연동과 배포·복구는 운영 환경을 확인한 뒤 진행한다. 현재 기본 게시판 완료와 최종 IA에 맞춘 전체 서비스 완성을 구분해 보고한다.
