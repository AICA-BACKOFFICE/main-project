# 동료 README와 개발 제안서 비교

작성일: 2026-09-21  
비교 대상: [동료의 원본 README](README.md), [개발 제안서 read.md](../../read.md)

## 1. 비교의 전제

원본은 기술 스택, 기능, 권한, DB, API, 배포까지 넓게 정리한 설계 초안이다. 새 제안서는 이를 바탕으로 기술 검증 순서와 초기 구현 범위, 두 사람의 작업 분담을 구체화한다.

원본 ZIP에는 README만 들어 있었다. 따라서 이 비교는 코드 품질이나 이미 구현된 기능에 대한 평가가 아니다. 원본에서 현재형으로 설명한 실행·테스트·배포도 이 폴더에서 확인된 구현으로 간주하지 않는다. 이 문서를 추가하면서 원본 README는 수정하지 않았다.

차이는 사실관계 수정, 구현 방식 변경 제안, 기존 설계의 구체화로 구분한다. 단순한 취향 차이를 기술 오류로 표시하지 않는다.

## 3. 우선 수정할 사실관계

원본의 1장에는 RTE 4.3.0이 Spring Boot 3.x / Jakarta EE 10 기반이라는 설명이 있다. 전자정부 공식 4.3 마이그레이션 가이드는 Spring Framework 5.3.37을 기준으로 안내한다. 이 설명은 수정이 필요하다. [전자정부 공식 가이드](https://www.egovframe.go.kr/wiki/doku.php?id=egovframework:rtemigration4.3)

반면 Boot 3.4.5 / Framework 6.2.6 / Security 6.4.5 / Tomcat 10.1.40은 Spring Boot 공식 릴리스와 일치한다. 이 Spring 구성에 RTE 4.3.0을 적용하는 범위가 검증 대상이다. [공식 릴리스](https://github.com/spring-projects/spring-boot/releases/tag/v3.4.5)

새 제안서는 무조건 결합할 수 없다고 단정하거나 버전을 임의로 낮추지 않는다. 실제 RTE 의존성과 사용 기능을 정해 검증하고, 충돌 시 담당자와 기술 조건을 조정하도록 한다. 현재 호환성 검증 결과는 아직 없다.

## 4. JWT에서 세션으로 바꾸자는 이유

원본의 JWT 설계는 Access/Refresh 토큰, 토큰 재발급 API, Refresh Token 해시 저장 등을 포함한다. 별도 프론트엔드나 외부 API 인증이 필요하다면 검토할 수 있는 방식이다.

현재 목표는 Thymeleaf로 제공하는 하나의 관리자 웹이다. 새 제안서는 서버가 로그인 상태를 관리하는 세션을 선택해 초기 인증 흐름을 단순화한다. Spring Security는 세션을 통한 인증 상태 유지를 지원한다. [공식 세션 관리 문서](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)

세션 방식에도 필요한 작업이 있다. CSRF 검증, 세션 만료와 로그아웃, 계정 변경 시 기존 세션 무효화를 구현해야 한다. 다중 서버에서는 공유 세션 저장 방식을 정해야 한다. JWT보다 항상 우월하다는 주장이 아니라 현재 구성에 대한 선택이다.

계정 비활성화·권한 변경·비밀번호 초기화 시 `auth_version`을 증가시키고 다음 보호된 요청에서 계정 상태와 버전을 확인하는 것은 새 제안의 구체적인 구현안이다. 세션을 선택하면 자동으로 해결되는 기능으로 설명하지 않는다.

## 5. 그대로 유지하는 설계

- 일반 회원가입 없이 최상위 관리자가 서브 관리자 계정을 발급한다.
- SUPER_ADMIN과 ADMIN 두 역할로 시작한다.
- 비밀번호는 BCrypt 해시로 저장한다.
- 신규·초기화 계정은 임시 비밀번호 변경을 강제한다.
- 화면 노출과 별개로 서버에서 권한을 검사한다.
- 마지막 최상위 관리자와 자기 계정의 권한·활성 상태를 보호한다.
- 게시물은 등록·수정·삭제를 제공하고 삭제 시각을 기록하는 방식을 제안한다.
- MyBatis, Thymeleaf, 스키마 마이그레이션과 감사 기록 방향을 유지한다.

위 항목들은 원본에 이미 들어 있다. 새 문서에서는 실제 적용 조건과 확인 시나리오를 더 명확하게 만든다.

## 6. 새 제안에서 줄이거나 추가한 범위

| 구분 | 내용 | 개발에 미치는 영향 |
| --- | --- | --- |
| 초기 범위 축소 | 토큰 재발급과 refresh_tokens | 세션으로 대체되므로 토큰 관리 구현 제거 |
| 후속으로 이동 | 감사 로그 전용 조회 화면 | 기록은 남기고 운영 조회 UI는 후속 작업 |
| 필요 확인 후 추가 | HTML 에디터·이미지·첨부 | 게시물 용도 확인 전에는 일반 텍스트로 구현 |
| 초기 필수에서 제외 | 모든 기능의 REST API·Swagger 구성 | 화면 폼 중심으로 시작하고 JSON API가 필요하면 추가 |
| 구현안 추가 | auth_version을 통한 기존 로그인 차단 | 계정 변경 효과가 다음 요청부터 반영되도록 검증 |
| 완료 기준 추가 | 계정 발급부터 게시물 관리까지 연결된 흐름 | 개별 화면만 완성한 상태와 실제 사용 가능한 상태를 구분 |
| 협업 방식 추가 | 인증·계정 담당 / 게시물 담당 | 각 담당자가 서버·화면·검증을 함께 책임짐 |

이 항목들은 고객의 추가 요구사항으로 확정된 것이 아니다. 새 개발 제안서에 담긴 우선순위와 구현 선택이다.

## 7. 두 사람이 먼저 맞출 사항

1. 기술 조건의 필수 여부와 최소 프로젝트 검증 결과
2. 운영 DB, 로그인 식별값, 기존 서비스 인증·데이터 연결 방식
3. 서브 관리자가 타인의 게시물도 편집할 수 있는지
4. 게시물 공개·HTML·이미지·첨부 기능이 1차에 필요한지
5. 공통 보안 코드·오류 형식·레이아웃·DB 마이그레이션 규칙
6. 실제 코드 저장소에서의 기능별 담당과 PR 검증 기준

원본의 기능 방향을 유지하면서 위 결정 사항을 정리한 뒤 구현을 시작한다. 화면 시안이 없어도 기본 폼으로 기능 개발은 진행할 수 있지만, 기존 서비스 정보가 없는 상태에서 연동 완료까지 약속하지 않는다.
