1요약

이 프로젝트는 블로그형 콘텐츠를 관리하는 관리자 웹(백오피스)입니다. 관리자는 로그인 후 게시물을 블록 에디터로 작성·발행하고, 카테고리·관리자 계정·방문 통계를 관리합니다. 프런트(공개 홈페이지)는 /api/public/** JSON API로 발행된 글을 읽어 갑니다.

한 줄 구조 — 브라우저 → Spring Security(세션 로그인·역할) → Controller → Service → MyBatis Mapper(XML) → H2 파일 DB. 화면은 Thymeleaf가 서버에서 렌더링하고, 글쓰기 화면만 바닐라 JS 블록 에디터가 동작합니다.

현재 패키지 분류 방식

Java는 이미 기능 단위 패키지(post, category, adminuser, image, stats, template …)로 나뉘어 있습니다. 다만 다음 세 가지 때문에 "기능별로 파일을 찾기"가 아직 불편합니다.

  • 기능과 자원이 흩어져 있음: 한 기능(예: 게시물)의 Java는 post/에, 화면은 templates/post/, SQL은 mapper/PostMapper.xml, 스타일은 admin.css·editor.css에 나뉘어 있어 4~5곳을 오가야 합니다.
  • 거대 파일: block-editor.js 1,226줄(에디터 전체), editor.html 495줄(페이지 + 인라인 JS 330줄), BlockContent.java 278줄, PostController.java 244줄(목록·편집·휴지통·버전·미리보기가 한 파일).
  • 잔재 파일: Stage0 검증용·샘플 데이터·구 폼 등 1줄짜리 자리표시자 파일 7개, 통합되지 않은 src/compatibility 소스 세트.

기동 순서

  1. BackofficeApplication 시작 → application.yml 로드 → 데이터소스·Flyway 실행(V1 스키마, V2 버전 이력, V3 템플릿).
  2. MyBatis가 classpath:mapper/**/*.xml을 읽고 @Mapper 인터페이스와 네임스페이스로 연결.
  3. InitialAdminRunner가 관리자 계정이 하나도 없으면 backoffice.initial-admin 설정으로 최초 SUPER_ADMIN 생성(임시 비밀번호 상태).
  4. SecurityConfig가 필터 체인 구성: 공개 경로(/login, /css, /js, /img, /uploads, /api/public, /h2-console)와 역할별 제한 경로 등록.
  5. 8080 포트에서 대기. / 접속 시 /admin으로, 미로그인 시 /login으로 이동.

4요청 처리 흐름 (한 요청이 지나가는 길)

관리자가 "게시물 목록"을 여는 경우를 예로 들면 다음 순서로 파일을 거칩니다.

① 브라우저GET /admin/posts?status=PUBLISHED
→
② SecurityConfig세션 확인 · 역할 규칙 (미로그인 → /login)
→
③ PostController.listPostSearch 바인딩 · menu="posts"
→
④ PostService.search@Transactional(readOnly)
→
⑤ PostMapper.xmlsearch / countSearch SQL
→
⑥ H2posts ⋈ categories ⋈ admin_users
⑦ GlobalModelAdvicesiteName · envLabel · frontBaseUrl · me(현재 관리자) 주입
→
⑧ post/list.htmlth:replace layout/admin :: layout(제목, 본문, 스크립트)
→
⑨ layout/admin.htmlGNB·좌측 메뉴·푸터 + admin.css · admin.js

계층별 역할 규칙 (현재 코드가 따르는 암묵적 규칙)

계층책임예
ControllerURL 매핑, 폼 바인딩/검증(@Valid), 모델 구성, 리다이렉트·플래시 토스트. 화면용은 @Controller, JSON은 @ResponseBody/@RestControllerPostController, PostTemplateController
Service트랜잭션, 업무 규칙(상태 전이, 삭제 가능 여부, 버전 기록), 예외(BusinessException/NotFoundException)PostService, CategoryService
Mapper (인터페이스+XML)SQL. 인터페이스 FQN = XML namespace. 결과 타입은 별칭(클래스 단순명)PostMapper ↔ PostMapper.xml
도메인/폼 객체Lombok @Getter/@Setter POJO. Form은 화면 입력, Entity는 DB 행Post, PostForm, PostSearch
공통예외 처리(HTML/JSON 분기), 모델 공통 속성, 페이지 결과common/*
참고 예외 처리는 두 갈래입니다. 화면 컨트롤러는 GlobalExceptionHandler가 error.html을 렌더하고, JSON 컨트롤러(이미지·템플릿)는 각자 @ExceptionHandler로 {"message":…}를 돌려줍니다. 업로드 용량 초과는 요청 경로(/admin/images)로 분기합니다.

6주요 동작 시나리오

6.1 글 작성 → 저장 → 발행

  1. GET /admin/posts/new → PostController.createForm이 빈 PostForm과 카테고리 목록을 모델에 넣고 post/editor.html 렌더.
  2. 에디터 JS가 hidden blocksJson을 파싱해 블록을 그림. 입력할 때마다 onChange → markDirty → 3초 뒤 localStorage(키 aica-draft-<id|new>)에 백업.
  3. [임시저장] 또는 [저장] 클릭 → 우측 패널의 공개 상태 select 값이 hidden status에 복사 → form.requestSubmit() (제출 직전 editor.sync()로 블록 JSON 갱신).
  4. POST /admin/posts → @Valid PostForm → PostService.create: BlockContent.parse → sanitize(허용 블록·태그·style·글꼴만 남김) → 요약 비면 plainText(160자) → 대표 이미지 AUTO면 첫 이미지 URL → insert → PUBLISHED면 publishedAt 설정 → recordVersion(PUBLISH|MANUAL_DRAFT).
  5. 성공 시 redirect:/admin/posts/{id}/edit + 플래시 토스트. 실패(검증 오류)는 같은 화면을 다시 렌더.
보안 포인트 클라이언트 cleanInline()과 서버 BlockContent.cleanInline()이 같은 규칙을 이중으로 적용합니다(태그 b/i/u/s/br/span/a/sub/sup/mark, style은 color/background/font-size/font-family/weight/style/decoration, 링크는 http/https/mailto). 서버 쪽이 최종 기준입니다.

6.2 이미지 삽입

  1. 도구 줄 [+ 사진] / 붙여넣기(Ctrl+V) / 드래그 앤 드롭 / 블록 안 파일 선택 → 모두 insertImages() 또는 doUpload() → 공용 upload().
  2. prepareImage(): JPG/PNG/WEBP가 300KB 초과면 이미지를 열어 긴 변 2000px 초과 또는 1.5MB 초과 시 캔버스로 축소(JPEG 0.86, 작은 PNG는 PNG 유지). 10MB 초과면 업로드 전에 오류.
  3. POST /admin/images (multipart, CSRF 헤더) → ImageStorageService.store: 10MB·형식 검사 → data/uploads/yyyy/MM/uuid.ext 저장 → images 테이블 기록 → {url, name, size} 응답.
  4. 에디터가 "업로드 중" 자리표시 블록을 실제 이미지 블록으로 교체, 실패하면 블록 제거 후 토스트.

6.3 휴지통 이동 · 복원 · 완전 삭제

POST /{id}/delete는 deleted_at만 기록(soft delete)하여 목록·공개 API에서 제외하고 휴지통 화면(GET /admin/posts/trash)에 표시합니다. restore는 deleted_at을 비워 삭제 전 상태 그대로 돌려놓고, purge는 post_versions → post_view_logs → posts 순으로 실제 삭제합니다(FK 순서). 세 동작 모두 ADMIN 이상만 허용됩니다.

6.4 버전 이력 복원

편집 화면 [버전 이력] → GET /{id}/versions(목록) → 항목 클릭 시 GET /{id}/versions/{vid}(블록 포함) → 오른쪽에 클라이언트 렌더. [편집기에 불러오기]는 저장 없이 블록만 교체, [이 버전으로 복원]은 POST …/restore로 서버가 현재 상태를 RESTORE_BACKUP으로 남긴 뒤 스냅샷으로 교체하고 RESTORE를 기록합니다. 공개 상태는 바꾸지 않습니다.

6.5 템플릿 저장·불러오기

[템플릿] 패널의 저장 버튼 → 이름 입력 → POST /admin/templates(JSON: name, titleHint, categoryId, blocksJson) → 서버가 블록을 정화해 저장. 목록은 블록 수·요약·첫 이미지를 포함해 카드로 표시되고, [불러오기]는 editor.setBlocks(), [뒤에 추가]는 editor.appendBlocks()로 반영한 뒤 markDirty()만 호출합니다(서버 저장은 사용자가 저장 버튼을 눌러야 함).

6.6 방문·조회 통계

프런트가 POST /api/public/track/visit, POST /api/public/track/posts/{id}/view를 호출하면 visit_logs/post_view_logs에 쌓이고 posts.view_count가 증가합니다. 관리자 홈(/admin)은 StatsService.summary(30)과 summary(7)로 KPI·일별 차트·인기글·게시물 현황을 만들고, 차트는 dashboard/index.html의 인라인 JS가 SVG로 그립니다. SUPPORT 역할은 홈 대신 글 관리로 이동합니다.
